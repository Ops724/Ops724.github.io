Go 语言并发编程中 Channel、Mutex 该如何选择

2026-08-04 编程语言 #Go
中 EN

这是一篇写于当时语境下的技术记录。技术发展日新月异，若其中某些方法、结论或版本信息已经过时，就把它当作一次技术考古吧。

需求：100 个协程，每个协程累加 1000 次，最终结果必须是 100,000。

  1. Mutex 方式（保护共享状态，共享内存+锁），这是最正统的做法。多个协程去修改同一个变量，加一把锁保护起来。
package main

import (
    "fmt"
    "sync"
)

var count int
var mu sync.Mutex
var wg sync.WaitGroup

func main() {
    for i := 0; i < 100; i++ {
        wg.Add(1)
        go func() {
            defer wg.Done()
            for j := 0; j < 1000; j++ {
                mu.Lock()       // 加锁
                count++         // 修改共享变量
                mu.Unlock()     // 解锁
            }
        }()
    }
    wg.Wait()
    fmt.Println("Mutex 最终结果:", count) // 100000
}
  1. channel 方式来模拟 Mutex 的效果实现这个计数，在 Go 语言中被称为 “令牌模式”（Token Pattern）。
package main

import (
    "fmt"
    "sync"
)

var count int
lockCh := make(chan struct{}, 1) // 创建一个容量为 1 的 Channel 作为锁
lockCh <- struct{}{}             // 初始化放入一个令牌

func main () {
	for i := 0; i < 100; i++ {
	    wg.Add(1)
    	go func () {
			defer wg.Done()
			for j := 0; j < loopCount; j++ {
	    		<-lockCh             // 获取锁：从 Channel 中取出令牌（如果没令牌，这里会自动阻塞等待）
        		count++              // 临界区：执行累加操作
        		lockCh <- struct{}{} // 释放锁：将令牌放回 Channel，唤醒其他等待的协程
			}
		} ()
	}
	wg.Wait()
	fmt.Println("Channel lock 最终结果:", count)
}

针对上述两种实现方式进行基准测试

package main

import "testing"

func BenchmarkMutexCount(b *testing.B) {
	var count int
	var mu sync.Mutex

	b.RunParallel(func(pb *testing.PB) { // 模拟多协程并发
		for pb.Next() {
			mu.Lock()
			count++
			mu.Unlock()
		}
	})
}

func BenchmarkChannelCount(b *testing.B) {
    var count int
    lockCh := make(chan struct{}, 1)
    lockCh <- struct{}{}
	
	b.RunParallel(func(pb *testing.PB) { // 模拟多协程并发
		for pb.Next() {
	    	<-lockCh
        	count++
        	lockCh <- struct{}{}
		}
	})
}


从基准测试结果看在累加计数场景中，channel 的方式性能远远落后于 mutex 的传统方式将尽两倍。

因为 Channel 的底层结构体内部本身就包含了一把互斥锁（hchan.mutex），外加一个环形缓冲区（buf）和两个等待队列（sendq、recvq）。

  • 当执行 <-lockCh（获取锁）时，底层需要：获取 hchan.mutex -> 检查缓冲区 -> 从 buf 拷贝数据 -> 释放锁。
  • 当你执行 lockCh <- struct{}{}（释放锁）时，底层需要：再次获取 hchan.mutex -> 检查缓冲区 -> 将数据拷贝进 buf -> 释放锁。

用 Channel 模拟锁，本质上是在一把锁的外面，又套了一层更重的锁，并且每次进出还要经历数据的内存拷贝。

总结

用 Channel 模拟锁，是非常符合 Go 语言那句著名口号的：“不要通过共享内存来通信，而是通过通信来共享内存。”

但在真实的工程实践中：

  • Channel 的主场：跨协程传递数据、构建流水线、发送退出信号。
  • Mutex 的主场：保护共享状态（比如缓存、计数器、Map）。Go 官方标准库里的 sync.Map、sync.Pool、net/http 的连接管理，全都是用 Mutex 保护的，没有一个用 Channel 做状态保护。

所以，用 Channel 模拟锁确实更有对比性，但它完美地证明了：在纯粹的“保护共享内存”这个场景下，专门设计的并发原语（Mutex/Atomic）在性能上是碾压 Channel 的。
